# H-01: Refund path can permanently strand user funds

## Summary

The failed-message refund path uses the wrong payload when reconstructing the refund operation.

Instead of using the preserved refund payload, `refund()` reads the already-mutated working `sendParam`. In the vulnerable flow, `sendParam.amountLD` has already been zeroed, so the refund path can no longer reconstruct the real amount that must be returned.

## Invariant

If a failed cross-chain action enters the refund path, the refund logic must use the intact refund payload, not a mutated runtime copy of the original send parameters.

## Root cause

The contract uses:

- `failedMessage.sendParam`

where it should use:

- `failedMessage.refundSendParam`

That creates a payload mismatch between:

1. the state saved for retry / refund
2. the state later consumed by `refund()`

## Impact

User funds can become permanently stuck or logically lost because the refund path no longer carries the original amount that must be returned.

## Fix direction

Use the preserved refund payload consistently during refund execution and ensure no mutated working copy can replace it in the recovery path.
