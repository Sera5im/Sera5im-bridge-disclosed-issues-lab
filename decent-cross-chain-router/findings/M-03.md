# M-03: Public receiveFromBridge path bypasses fee collection and signed instruction enforcement

## Summary

`UTB.receiveFromBridge(...)` is publicly callable and forwards execution straight into `_swapAndExecute(...)`.

Unlike the normal public entrypoints, it does not pass through the fee-collection and signature-validation flow. As a result, a user can execute the post-bridge path directly, avoid paying bridge fees, and run arbitrary unsigned instructions.

## Invariant

Any user-reachable execution path that performs the same swap / execute behavior as the normal UTB flow must preserve the same fee collection and signed instruction checks.

## Root cause

`swapAndExecute(...)` and `bridgeAndExecute(...)` are guarded by the fee retrieval and validator-signature flow.

`receiveFromBridge(...)` is not. It is public and directly calls the internal execution path.

That creates a cheaper and less trusted alternate route to the same privileged behavior.

## Impact

Users can bypass fee collection and run unsigned swap / execution instructions through the public receive path.

This breaks the expected fee model and weakens the protocol's trust boundary around validated bridge-delivered instructions.

## Fix direction

Restrict `receiveFromBridge(...)` so only the trusted bridge-side component can call it, or enforce an equivalent authenticated delivery check before allowing execution.
