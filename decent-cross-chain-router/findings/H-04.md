# H-04: Reserve shortfall can strand bridged value inside the destination-side adapter

## Summary

When the destination router receives bridged `dcntEth`, it checks whether it has enough local `WETH` reserves to complete the intended delivery.

If reserves are insufficient, the router does not preserve a user-owned refund path. Instead, it transfers the received `dcntEth` to `_to`.

Under the payload execution route, `_to` is not the end user. It is the destination execution target, which is commonly the destination bridge adapter. That means the bridged value can be pushed into a contract that has no user withdrawal path, effectively stranding the cross-chain transaction.

## Invariant

If destination-side liquidity is insufficient, the fallback path must still preserve user ownership of the bridged claim and must not redirect value into an execution-only contract that the user does not control.

## Root cause

The reserve-shortfall branch in `DecentEthRouter.onOFTReceived(...)` sends `dcntEth` to `_to`.

That is only safe for plain transfer-style messages. It is unsafe for payload-bearing execution messages because `_to` represents the destination execution target, not the intended user refund address.

## Impact

If the destination router runs short on `WETH`, payload-bearing bridge transactions can be stranded.

The user loses practical control over the bridged claim because the fallback asset is transferred into the destination adapter / target contract instead of a user-controlled refund recipient.

## Fix direction

Encode and use an explicit destination-side refund address for the reserve-shortfall branch instead of reusing `_to`.
